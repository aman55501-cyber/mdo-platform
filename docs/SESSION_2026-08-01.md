So the job was: bring Shares CFO onto the Life-LLM line.

### What came across

`shares_cfo/` (brokers, analysis stack, execution engine + guardrails, MCP server, agent
charter), `mobile/` (React Native app), `handoff/life-os` + `handoff/business-os`, and the
Caddy/autoheal deployment pieces.

### Conflicts — only 3 files, but one hid a real bug

- **`docker-compose.yml`** — unified into one nine-service stack. Because `sharescfo` now
  sits on the same network as the backend, `CFO_API_URL: http://sharescfo:8000` just
  resolves. The cross-stack hack `docker network connect sharecfo_default …` is gone.
- **`.env.example`** — both halves now read the *same* file, so duplicate keys silently
  override. `CFO_API_TOKEN` was being blanked by a second definition, which would have
  broken CFO auth on first deploy.
- **`.gitignore`** — union of both.

**A bug the merge would have introduced, outside the conflicts:** `vega` and Shares CFO both
read `HDFC_BASE_URL`, but vega appends its own `/api/v1` to the *auth* host while Shares CFO
points at the *API* host (`…/oapi/v1`). One shared `.env` would have silently corrupted
vega's auth URLs — no error, just failing requests. Vega's config now reads
`VEGA_HDFC_BASE_URL`.

## 3. The interview — 3 questions of a 14 budget

### Q1 — What is v1?

**Asked:** the one brain you *ask* (chat surface, all tools) or the one feed that *tells* you
(threshold-gated push)?

**Answer: the feed.** Being the bottleneck is an interruption problem; a pull-only assistant

### Q2 — What may an alert do?

**Asked:** inform only, or arrive with a drafted action approved in one tap?

**Answer: propose-and-approve, money excluded.** The efficiency is in the *deciding*, not the

**Asked:** chat buttons in the notification, or deep-link into the app?

This one turned on evidence. `vega/telegram_bot/` already had a complete confirm/reject
inline-keyboard loop wired to a trade engine — reviving it was the *cheap* build. But the

> — `MDO_VISION.md:450`

Surfaced rather than silently overridden. **Answer: deep link into the app.** That bot stays
dormant.

After Q3 the human delegated the rest ("I will follow all your recommendations"), so every
remaining fork became a tagged default in `PLAN.md`'s Assumptions Ledger.

## 4. What got built

### The Decision Feed — `mdo_feed.py`

The spine. Every producer calls one function, `publish()`, so dedup, cooldown and severity
routing cannot be bypassed by adding a new source later.

Severity decides delivery: `critical` pushes now, `important` batches into a digest, `info`
waits in the app.

Actions carry a **kind**, and the kind is what approval enforces:

| Kind | Example | On approval |
|---|---|---|
| `internal` | file a task, file intel | executes |
| `outward` | WhatsApp a site head | executes — full text shown first, always audited |
| `money` | place an order | **refused**, recorded, never executed |

The money refusal is policy on the approval path, not a missing button. The test registers a
live order handler and asserts it is never called.

### Site access over the VPNs — `mdo_sites.py`

The sidecars existed and compose passed `HOTEL_PROXY_URL`/`VEDANTA_PROXY_URL` into the
backend — but **no code read them** (verified by grep before the change). This is that layer:
read-only (`SAFE_METHODS = ("GET",)`), tunnel health per site, and a dead tunnel publishing a
critical finding, because site data going missing is itself the alert.

It invents no site hostnames. Those LANs have never been scanned, so sources are *configured*
via `MDO_SITE_SOURCES` / `site_sources.json`; with none set the API says "no sources
configured". A moved JSON field reads as an error, never as zero.

### The capital keyhole — `mdo_brain.py`

The brain had 22 tools and exactly **one** touched capital — answering questions about a live
book through a single summary. Added seven capital tools through the CFO bridge, plus site and
feed tools. A test asserts every declared tool has a dispatch branch.

### Broker-session freshness

Aman last ran the HDFC login *yesterday*, and those tokens expire daily. That failure is
silent: nothing errors, the app renders, the briefing generates — the capital numbers are just
absent. `POST /api/feed/check-sessions` publishes the absence at three levels:

- bridge unreachable → **critical** (every capital number is gone)
- account(s) logged out → **important**, naming which, with the re-login task drafted
- authenticated but stale → **important** (logins fine, data rotting)

### The one page — `mdo-app/app/feed/`

`/feed` (list, critical first) and `/feed/[id]` (the deep-link target a push lands on). Money
items render read-only with the reason; outward items show the exact message before the tap;
the empty state says *nothing needs you* rather than showing a blank screen.

### Everything else

`deploy.sh` (one-command deploy with preconditions), `GO_LIVE.md`, `PLAN.md`, root `README.md`,
raw TCP forwards in the VPN sidecar, and profile validation.

## 5. Decisions made (also appended to `MDO_VISION.md` §17)

| Decision | Reasoning |
|---|---|
| Merge Shares CFO into MDO — one repo, one stack | Two codebases, two front doors, two brains; capital was behind a cross-stack bridge |
| Decision Feed is the product surface | One queue of what needs Aman, pushed, with the action drafted |
| Money actions never execute from an approval tap | Real money, four live accounts; enforced on the approval path |
| Hotel occupancy comes from the site server over VPN, not Staah | Only an ID/password exists, no API token; **Staah is cloud so the VPN cannot reach it** |
| One hostname (`srv1641037.hstgr.cloud`) routed by path | HDFC's registered redirect is the fixed point |

### Why the Staah call matters

The tunnel and Staah are not two routes to the same data — they are routes to *different*
data. Staah holds cloud OTA channel inventory; the site server holds what is happening at the
property. Without an API token the only Staah path left is driving the portal with credentials
from a headless browser, which is fragile and breaks on any reskin. The WhatsApp "Daily Sales
Report" parsing keeps running underneath as the manual fallback.

## 6. The HDFC callback trap

Aman registered `https://srv1641037.hstgr.cloud/hdfc/callback`. That path is **Shares CFO's**
route, not MDO's — which was correct, but the merge had made it a coin flip. The two callbacks
arm different things:

| Handler | Writes to | Used by |
|---|---|---|
| MDO `/api/hdfc/callback` | `hdfc_session` table | only `/api/hdfc/funds` |
| **CFO `/hdfc/callback`** | `token_store` | **`/accounts` `logged_in`, and every capital number** |

Point HDFC at the wrong one and it fails in the worst available way: a green *"✓ HDFC
connected"* page while the broker sessions stay logged out.

Three fixes: Caddy routes one hostname by path (`/api/*`, `/mcp/*` → backend; `/hdfc/*` →
Shares CFO; `/*` → app); Shares CFO's port 8000 is published again (its pages link to absolute
paths that would collide under a prefix); MDO's callback `307`s the request token to
`CFO_PUBLIC_URL` rather than spending it, since the token is single-use.

> ⚠️ **If the domain ever changes, change it at developer.hdfcsec.com in the same sitting.** A
> stale redirect URL does not error — the login just never completes and capital goes blind.

## 7. The VPN profiles

Both files in Drive (`hotel vpn`, `vedanta vpn`) were **byte-identical** — same SHA-256, same
gateway, same certificate, same private key. Deployed as-is, both sidecars would have dialled
one gateway, leaving a site silently unreachable while looking healthy, and two connections
presenting one certificate would knock each other offline.

Flagged; a genuine Vedanta profile was supplied. Now verified distinct:

| | Hotel | Vedanta |
|---|---|---|
| Gateway | `182.65.204.86:1194` | `103.251.31.130:1194` |
| CA fingerprint | `DD:45:19:A4…` | `68:16:F6:1C…` |
| Issued | 30 Jul 2026 | 11 Apr 2026 |

Different CAs = separate Omada controllers, so the shared CN is not a collision. Both keys are
1024-bit RSA — the controller's choice, already recorded as accepted residual risk.

**Attempted from the session:** bringing the hotel tunnel up here to run discovery directly.
OpenVPN parsed the profile, resolved the remote and sent packets, but got no response in 60s —
this environment's egress is HTTPS-via-proxy only, so UDP/1194 cannot leave. Environment
limit, not a profile fault.

### IDS Next broke an assumption

The hotel runs **IDS Next FortuneNext**, which on-premise is a **SQL Server application** —
installation is creating a database in SQL Server, setting permissions, restoring from backup.
No public API; integrations go through the vendor or middleware like CHAR PMSLINK.

That killed assumption A8 ("site hosts speak HTTP"). tinyproxy carries HTTP and nothing else,
so as built the sidecar could never have reached the PMS. `docs/PLAN_VPN_SITE_ACCESS.md` had
predicted exactly this and named the fallback, so the sidecar now also does raw TCP forwards
via socat:

```
HOTEL_TCP_FORWARDS=1433:10.0.0.5:1433
```

Bound inside the container network only. **Deliberately not built:** querying the database.
That needs credentials (excluded by that plan's R9) and the IDS schema, which is not public
and cannot be guessed.

## 8. Bugs found and fixed

### In the existing codebase

1. **`HDFC_BASE_URL` collision** — would have silently corrupted vega's auth URLs under one
   shared `.env`.
2. **`CFO_API_TOKEN` blanked by a duplicate definition** in the merged `.env.example`.
3. **Action registry was process-global and clearable** — left the server with no handlers, so
   *every approval would have failed* with "no handler registered". Found by test ordering.
   Registration is now idempotent via `register_feed_actions()`.

### In code written this session

4. **Cooldown boundary** — a cooldown of 0 suppressed everything instead of nothing.
5. **Expiry boundary** — strict `<` never expired an item whose expiry equalled now.
6. **`decide()` shadowed `result`** with two different types; the handler's return now travels
   as `action_result`.

### In `deploy.sh` (found on the live VPS)

7. **Stopped the old stack, then aborted** on a failing check — left the capital surface down
   with nothing in its place. The fatal gate now sits before anything is stopped.
8. **Volume migration wrote to the wrong prefix.** The project name was derived by sanitising
   the directory name with `tr -cd 'a-z0-9'`, which strips hyphens: `mdo-platform` →
   `mdoplatform`. It reported success while compose used `mdo-platform_*`, empty. The name now
   comes from `docker compose config`.
9. **Migration skipped when the destination merely existed** — after a first start compose has
   already created it, empty, so retries never copied. It now checks for content.
10. **An empty VPN profile was FAIL**, blocking the whole deploy over an optional feature; and
    sidecars without a usable profile were started anyway, restart-looping forever.

## 12. The through-line

Most of what was built exists to stop the system lying quietly. A dead tunnel, an expired
broker login, a moved JSON field, a suppressed duplicate, a mis-registered OAuth callback —
each of these fails *silently*, leaving a calm-looking screen with nothing behind it. A
dashboard that says "I lost this feed" is worth more than one that shows a confident zero.
